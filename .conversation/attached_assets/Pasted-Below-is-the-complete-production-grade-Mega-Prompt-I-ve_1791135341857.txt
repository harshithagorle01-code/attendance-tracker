# 2. Core Mission Directive

Build a complete web application named **AttendSmart** that allows students to accurately track academic attendance in real time.

The system must combine:

1. Daily attendance logging
2. Subject-wise attendance tracking
3. Real-time percentage calculation
4. Attendance risk classification
5. Safe-bunk calculation
6. Required-attendance recovery calculation
7. Timetable management
8. Daily schedule visualization
9. Cancelled-class management
10. Duty Leave / OD management
11. Medical Leave management
12. Supporting-document uploads
13. Credit-aware attendance analytics
14. Offline-first attendance logging
15. Automatic synchronization when connectivity returns
16. Proactive reminders
17. AI-powered attendance advisory
18. Historical attendance analytics
19. Dashboard-based academic insights
20. Secure cloud persistence

The application must provide students with a single reliable source of truth for their attendance records.

The system must never silently lose attendance data.

Offline attendance actions must be queued locally and synchronized safely when the connection is restored.

All important calculations must be performed deterministically by the application/backend rather than delegated blindly to an AI model.

AI should provide explanations, recommendations, summaries, and planning assistance—not authoritative mathematical calculations.

# 3. Product Goal

The goal of AttendSmart is to solve the visibility, accuracy, and planning problems caused by delayed institutional attendance systems and manual attendance tracking.

The application should allow a student to immediately answer:

* What is my attendance percentage?
* Which subjects are below the required threshold?
* Which subjects are at risk?
* How many classes can I safely miss?
* How many consecutive classes do I need to attend to recover?
* What classes do I have today?
* Which classes have already been logged?
* Which classes were cancelled?
* Which absences are covered by OD or medical leave?
* How are my credits affecting overall attendance?
* Am I academically at risk?
* What should I prioritize this week?
* What happens to my percentage if I attend or miss upcoming classes?

The product must feel simple enough for a student to use multiple times per day.

## 4.11 Dynamic Bunk Calculator

Implement deterministic calculations.

Given:

```text
A = classes attended
C = classes conducted
T = target attendance rate
```

Current attendance:

```text
Percentage = (A / C) × 100
```

Safe bunks:

```text
Safe Bunks =
floor((A - (T × C)) / T)
```

Never return a negative safe-bunk value.

Minimum:

```text
0
```

---

## 4.12 Required Attendance Calculator

Calculate the number of consecutive classes that must be attended to reach the target.

Formula:

```text
Required =
ceil(((T × C) - A) / (1 - T))
```

Never return a negative value.

If the current percentage is already at or above the target:

```text
Required = 0
```

* Credit-weighted attendance

* Practical attendance

* High-credit subject risk

Clearly label weighted analytics separately.

## 4.14 Offline-First Architecture

Attendance marking must work without an internet connection.

Use browser storage such as:

```text
IndexedDB
```

Maintain a local queue of unsynchronized mutations.

Each queued mutation must have:

* Client-generated UUID
* Operation type
* Entity ID
* Payload
* Created timestamp
* Retry count
* Synchronization status

When connectivity returns:

1. Detect connection.
2. Send queued operations.
3. Validate server response.
4. Mark successful operations synchronized.
5. Retry transient failures.
6. Prevent duplicate operations.
7. Preserve failed operations for later retry.
8. Update local cache.

The UI must clearly communicate:

```text
Online
Offline
Syncing
Synced
Sync error
```

## `student_profiles`

```sql
CREATE TABLE student_profiles (
    id UUID PRIMARY KEY,
    user_id UUID NOT NULL UNIQUE REFERENCES users(id) ON DELETE CASCADE,
    full_name TEXT NOT NULL,
    institution TEXT,
    academic_year TEXT,
    semester TEXT,
    program TEXT,
    attendance_target NUMERIC(5,2) NOT NULL DEFAULT 75.00,
    timezone TEXT NOT NULL DEFAULT 'Asia/Kolkata',
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT attendance_target_range
        CHECK (attendance_target >= 0 AND attendance_target <= 100)
);
```

---

## `subjects`

```sql
CREATE TABLE subjects (
    id UUID PRIMARY KEY,
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    name TEXT NOT NULL,
    code TEXT,
    faculty_name TEXT,
    credits NUMERIC(4,2) NOT NULL DEFAULT 1,
    subject_type TEXT NOT NULL DEFAULT 'Theory',
    target_attendance NUMERIC(5,2),
    is_archived BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT subject_type_valid
        CHECK (
            subject_type IN (
                'Theory',
                'Practical',
                'Lab',
                'Elective',
                'Seminar',
                'Project',
                'Other'
            )
        ),
    CONSTRAINT subject_credits_valid
        CHECK (credits >= 0),
    CONSTRAINT subject_target_valid
        CHECK (
            target_attendance IS NULL
            OR (
                target_attendance >= 0
                AND target_attendance <= 100
            )
        )
);
```

## `timetable_entries`

```sql
CREATE TABLE timetable_entries (
```

## `attendance_records`

```sql
CREATE TABLE attendance_records (
    id UUID PRIMARY KEY,
    client_id UUID,
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    subject_id UUID NOT NULL REFERENCES subjects(id) ON DELETE CASCADE,
    timetable_entry_id UUID REFERENCES timetable_entries(id) ON DELETE SET NULL,
    attendance_date DATE NOT NULL,
    start_time TIME,
    end_time TIME,
    status TEXT NOT NULL,
    notes TEXT,
    source TEXT NOT NULL DEFAULT 'online',
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT attendance_status_valid
        CHECK (
            status IN (
                'Present',
                'Absent',
                'Cancelled',
                'Duty Leave',
                'Medical Leave'
            )
        ),
    CONSTRAINT attendance_source_valid
        CHECK (
            source IN (
                'online',
                'offline_sync',
                'import'
            )
        ),
    UNIQUE(user_id, subject_id, attendance_date, start_time)
);
```

The `client_id` must be unique per user to support idempotent offline synchronization.

Create an appropriate unique index:

```sql
CREATE UNIQUE INDEX attendance_client_id_unique
ON attendance_records(user_id, client_id)
WHERE client_id IS NOT NULL;
```

# 11. Row Level Security (RLS) / Data Isolation Rules

Every user's data must be isolated.

A user must never be able to retrieve another user's:

* Subjects
* Attendance
* Timetable
* Leave requests
* Documents
* AI advisories
* Sync operations
* Profile data

Implement ownership validation at the backend.

If the PostgreSQL environment supports application-level RLS safely, enable RLS policies.

At minimum, every query must include authenticated ownership constraints.

Never trust:

```text
user_id
```

provided by the frontend.

The backend must derive the authenticated user identity from the authenticated session/token.

Example:

```text
WHERE user_id = authenticatedUser.id
```

Never accept arbitrary ownership identifiers from client payloads.

For nested resources, verify ownership through the parent entity.

## Mathematical

Verify:

```text
Percentage = (Attended / Conducted) × 100
```

Verify:

```text
Safe Bunks =
floor((Attended - Target × Conducted) / Target)
```

Verify:

```text
Required =
ceil((Target × Conducted - Attended) / (1 - Target))
```

Handle:

```text
0 conducted classes
0 attended classes
100% attendance
target already achieved
very low attendance
target = 0
target = 100
```

Avoid division-by-zero and invalid negative outputs.

For `Target = 100%`, recovery mathematics must be handled as a special case because the standard denominator `(1 - T)` becomes zero.

For example:

```text
If A = C:
    Required = 0
Else:
    Target cannot be recovered by finite future attendance alone.
```

Represent this state explicitly rather than returning infinity or crashing.
